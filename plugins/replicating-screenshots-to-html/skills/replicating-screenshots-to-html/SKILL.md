# Replicating Screenshots to HTML

## 核心原则

「看起来一样」不是判据。把差异变成数字，用同一套脚本量原图和复刻的渲染图，循环到数字收敛。

**全图 MAE / SSIM 会骗人** —— 它们被大片背景主导。实测有一次：某个 agent 报告
「MAE 2.76/255、SSIM 0.968、所有元素 bbox 误差 ≤1px」，逐行量墨量后发现
正文整体偏细 20%，整页的字都被画轻了。

**运行前提**：Python 3 + `numpy`/`Pillow`，本机 Chrome（`render.py` 自动探测常见路径，
也可 `CHROME=/path/to/chrome`，`python3 scripts/render.py --check` 可查）。
脚本本身跨平台（macOS / Linux / Windows），但**字体结论基于 macOS 的 PingFang / SF Pro**；
换平台后字号、字重、描边的标定要重跑。

**Windows 上命令名不一样**：没有 `python3`，下文所有 `python3` 一律换成 `python`；
也没有 bash，`render.sh` / `run_tests.sh` 不用，直接跑对应的 `.py`。三个脚本本身是纯 Python，
不含任何平台相关代码，换系统唯一要重做的是字体标定。

## 闭环

1. **定 dpr，定原点，量底色**：dpr = 原图宽 ÷ 设计宽（1170/390 = 3），用分隔线的两端落在
   设备像素整数上验证（实测落在 50 和 1120）。dpr 错了后面所有坐标都是错的，
   而且看起来只是「页面整体缩放不对」。
   背景灰度取**全图最常见的灰度**，不是默认 255：iOS 常见 `#F7F7F9` = **247**，
   按 255 量每个元素的墨量都会系统性偏重 8~12%，读起来像「字重没调对」。
   然后从**实心元素**（分隔线、色块、卡片边、图标直边）反推内容盒的
   `padding-left`。它的两端就是元素边界，量到设备像素整数。**别从文字反推** ——
   文字墨迹里混着字体侧边距，0.67px 的差异分不清是原点偏了还是字宽不同。
   有一次把 `--side` 从 16 改成 16.67（＝设备像素 50/1120），全图 MAE 5.996 → 3.998。
2. **量原图**：逐行切带、逐元素取 bbox、每字列区间，全部换算成 CSS px（设备像素 ÷ dpr）。
   **每个元素单独框一个矩形**：整行一个 bbox 会把行内的错位平均掉（见坑 19），
   而 `elems` 会按你给的清单逐个量，清单本身就逼你这么做。
3. **验字体真相**：`canvas.measureText` 实测 `font-family` 到底解析成什么，别按名字猜。
4. **写 HTML**：按 CSS px 写，`body{margin:0}`。想居中就用 `.phone{width:390px;margin:0 auto}`
   —— 视口由渲染器固定成 390，居中不会带来偏移。
5. **渲染**：`python3 scripts/render.py in.html out.png 390 844 3`
   （`bash scripts/render.sh` 是它的包装，等价）。dpr 必须和原图一致，
   否则抗锯齿和亚像素定位全不一样。
   渲染器用 iframe 固定视口：直接给 Chrome `--window-size=390` 会被最小窗口宽夹成 500，
   页面按 500 排版再裁左边 390，全页 x 坐标作废（见 `reference/metrics.md` 坑 15）。
6. **对比**：把每个元素的位置写进一份清单，一次跑完：
   `python3 scripts/measure.py elems --orig 原图 --mine out.png --rects rects.txt`
   清单每行 `名字,x0,x1,y0,y1[,阈值][,底色][,类型][,Y文字]`，`#` 注释，
   类型 `text`（默认）/`icon`/`line`，见 `reference/elements.example.txt`。
   输出四边 Δ（设备像素）、墨量比、IoU、局部 MAE —— 这是主判据。
   文字行两边段数一致时，整串首尾字心跨度差 ≥3% 还会直接给「字距」还是「字号/缩放」
   的归因（见坑 37），不必再单独跑 `cols`。
   **文字行只报数不给结论**（IoU 底噪 0.5–0.85）；`icon` 且强对比才按 0.80 判形状；
   1 设备像素的线标 `line`，按峰值行/列判墨量（横线看行、竖线看列；整窗比会被 JPEG 振铃污染）。
   局部 MAE 是低对比文字上最稳的信号，但**只比自己改动前后**，元素之间不可比。
   **清单先在原图上自比一次**：`--mine` 也传原图，四边必须全 0、墨量比 1.000、IoU 1.000。
   任何一项不是，先怀疑窗口/阈值/工具，别去改 CSS —— 零成本，比值完再分辨「这 0.54
   到底是底噪还是真错」便宜得多（坑 29）。
   再用 `rows` 看整屏行有没有错位、`mae` 看有没有整块偏移。
   `rows` 的主判据是 Δy；行带里混进图形、深色块时墨量比和字干都不作数（坑 28、30），
   拿它裁字重之前先确认这一带是纯文字。
   `box`/`cols` 留给单点复查；看到 `← 墨迹贴右边，窗口可能没框全` 就先把窗口放大，
   那不是结论（判据是**窗外还接着墨**，窗口正好等于墨迹框不会误报）。
7. 回到 4，直到数字收敛。**每渲染一版先 `md5sum`**：和上一版字节相同 = 这个旋钮
   死了（Chrome 把布局量化到整设备像素，0.1px 的微调常常什么都没改），别在上面耗。
   **改完先看整页 MAE / `rows` 有没有新的 Δy**：动一个块的上内边距、动一个字号，
   都可能把下面的元素整体推走（坑 18、20）。

## 判据

| 指标 | 判什么 | 过关线 |
|---|---|---|
| 逐行墨量比 | 字重、字号整体 | 0.97–1.03（超过 7% 是结构性偏差） |
| 细线峰值行墨量比 | 1 设备像素的线（`line`） | 0.90–1.10（源图自己的噪声底就到 7%）；整窗比会被 JPEG 振铃污染，不算数 |
| 竖向 Δy（墨迹质心） | 行/元素的位置 | ≤0.75px（噪声底 ~0.3） |
| 形状 IoU | 强对比、实心图标的形状 | > 0.80 |
| 文字块 IoU | 字形相位（bbox 和墨量都看不见的整串错位） | 没有绝对线，只看 ΔIoU |
| 局部 MAE | 低对比文字的总体差异 | 只比改动前后，窗口不同不可比 |
| 逐字列区间 | 字距、元素左右沿 | 差 ≤1 设备像素，且要看差落在**哪几个字**上 |

**文字的 IoU 不能拿 0.80 卡。** 它的底噪取决于渲染器是否同源：iOS 原图 vs Chrome 复刻，
即使 bbox 四边全 0、墨量 0.995，一段日期也只有 **0.72**，浅灰（`#999`）正文更低到 **0.52**
—— 字形栅格化本来就不同，浅色字的 JPEG 噪声又相对更大。
所以文字 IoU 只用来**比较改动前后**：补了字距从 0.70 升到 0.93 就留（实测全局 MAE
0.444 → 0.380，比任何单步都大），降了就回滚。反过来，bbox 和墨量都对、IoU 却明显低于
同页其他文字时，说明整串字有亚像素相位差，先试 `letter-spacing`，别动字号。

**细描边 + 低对比的图标同一条命。** 1 设备像素宽的 `#C6C6C6` 箭头，四边都在 1 设备像素内、
墨量差 2.5%，IoU 只有 **0.54** —— 对比度只有 49 个灰度，JPEG 噪声在覆盖率里占比太大。
所以 `elems` 只对 `icon` 且 `|bg−Y文字| ≥ 100` 的元素按 0.80 判形状；
浅灰细线图标按 bbox + 墨量判。

Δy 用**墨迹质心**（墨量的一阶矩），不用 bbox 上沿：浅灰文字贴阈值时 bbox 会跳 ±2px，
质心对阈值和模糊都不敏感。实测 bbox 报「+0.3」的那次，质心给出的是真实的 +1.33px。
门槛是 0.75 而不是 0.5：同一段内容在四张卡里重复三次，质心读数相差 0.3px
（JPEG 8×8 块的相位不同），卡到 0.5 会把自己的噪声当成还没对齐。

墨量 = `Σ clip((255−gray)/255,0,1)`。高斯模糊下近似守恒，所以被 JPEG 糊过的截图也能量准。
定义、阈值和全部踩过的坑见 `reference/metrics.md`。

三个文件分别跑 `python -I tests/test_measure.py`／`test_trace_shape.py`／`test_render.py`；
断言对着解析解，不是对着上一次的输出）；红了就是破坏了已有语义。

## 常见错误（都是实测踩过的）

| 做法 | 为什么错 | 改成 |
|---|---|---|
| 用 MAE/SSIM 判断像不像 | 被背景主导，20% 的字重误差照样 SSIM 0.97 | 逐行墨量 |
| 信 `--window-size` 就是视口 | 被最小窗口宽夹到 500，页面按 500 排版，全页 x 偏移；**逐行墨量比照样好看**，只有 IoU 会掉到 0.1 | 用 `render.py`，先验 `innerWidth` |
| 用 `letter-spacing` 掩盖字重/字号错 | 字重或字号错了，靠拉字距把总宽凑上；总宽对了，每个字形还是错的 | 先把墨量比调到 0.97–1.03，再谈字距 |
| 宽度差就改字号 | 墨量本来是对的，缩小字号让**每个字都从原图笔画上滑开**，IoU 反而从 0.56 掉到 0.43 | 墨量对、只差宽度 → 只补字距；判定用 IoU 而不是宽度 |
| 右对齐的串先扫字号 | 容器的 `padding-right` 错了会**伪装成字号错**（扫了一圈 17.33/17.67，真凶是 padding 35→33.33） | 先量锚点，再扫字号 |
| 只改一侧内边距 | 块高变了，下面**整屏**跟着位移（实测 −1.66px，MAE 3.7→5.4） | 上内边距改多少，下内边距补回多少，总高不变 |
| 改了容器不重量子元素 | 子元素偏差会正好按移动量翻号（徽标 `-.67` 其实一直在补偿行本身的偏差） | 先修容器，再逐个重标子元素 |
| flex 行靠 `line-height` 定高 | `align-items:baseline` 的行交叉尺寸是 `max(基线以上)+max(基线以下)`，子元素字号一变就长高（0.25px × 4 张卡 = 底部 1.5px） | 在容器上钉死 `height` |
| 细线用 `.5px` / `box-shadow` | 0.5px 在 3x 下是 1.5 设备像素，必然跨两行、峰值偏浅 | 看它散在几行：1~2 行 → `.3333px` 实线；3~4 行渐变 → 同高的渐变。alpha 按**积分**取 |
| 下划线用默认位置 | `text-underline-offset` 差 0.3px 就落错一个设备行：实测 1.4px → IoU 0.804，1.1px → 0.885 | 量出线所在设备行再扫 offset；对不上就画独立的 1.3333px 条 |
| 写 `-apple-system` | macOS Chrome 解析成 PingFang，`2026-09` 的连字符宽 9 而不是 6 | `system-ui` |
| 加 `font-variant-numeric:tabular-nums` | SF Pro 等宽数字比比例数字宽 6% | 去掉 |
| 手绘复杂符号（wifi、蜂窝、电池轮廓） | SF Symbols 有可提取的光栅渲染，凭印象画只在像素上碰巧像 | `trace_shape.py --alpha` |
| 用 `trace_shape` 画几何图标 | 箭头、信号条、1 设备像素的边框、圆点、胶囊是**几何图元**；0.5 等值线会把 JPEG 光晕一起还原出来，1 设备像素的描边反而糊 | 写好参数、按 IoU 扫参数（实测描边 1.72 + 顶点 x 1.4 → 0.96） |
| 图标 IoU 低就直接改形状 | 1 设备像素的位置差能让 IoU 掉到 0.80 以下；不先对齐就分不清「位置错」和「形状错」 | `elems` 会为强对比的图标自动做 ±2 对齐并标「位置差（对齐后 …）」；单点复查用 `iou --shift 4` |
| 白字/浅字在彩色底上只给 `--text-luma` | 背景不是白，覆盖率会算成整块底色：实测同一个按钮报 0.94（假）/ 0.81（真），格式完全正常 | 同时给 `--bg`（底色）和 `--text-luma`（字色）；工具会警告「一半以上被算成墨」 |
| 字重只当固定档位（400/500/700） | 原图的字重常常落在中间：28px/700 偏重 11.6%，改成 **29px/550** 才同时对上宽度和墨量 | 扫 size × weight × stroke 三维，别假定整数档 |
| 中文也按 550 找中间档 | PingFang 的汉字面只有几档（28px 实测逐字节相同：200≡300、350≡400≡450、600≡650≡700≡800），而 **550 是合成加粗：比 600 还重 12%、墨迹还外扩 0.67px** | 中文按 300/400/500/600 扫，中间值用字号和 `-webkit-text-stroke` 补；只有西文（system-ui → SF Pro）才是每 50 一档都变 |
| 描边固定 `.1px` | 小字号会明显过粗：11–12px 用 .04–.05，15px 的细数字用 .08 | 每个样式单独扫 0.02–0.1 |
| bbox 对上了就收工 | bbox 对得上、形状可以是斜的（问号实测如此） | 再算 IoU |
| 所有元素用同一个阈值 | 浅灰元素（`#C6C6C6` 灰度 198）贴在 200 上，bbox 跳 ±2px，会误报「偏了 1.7px」 | `--thr` 取 (最淡元素灰度 + 背景)/2：浅底 255 配 198 → 226 |
| 深色底沿用默认 `--thr 200` | 阈值是「离底色多远算墨」，深底 30 上等价于只认灰度 >200：中灰文字（`#6B7078`=108）、灰细线**全部静默消失**——实测同一页 18 条带只剩 6 条，而表格照样报「0.0%」 | 阈值跟着底色走：bg 30 配最淡的 108 → 69。工具现在会警告「把灰度 0~200 当成了背景」 |
| 背景默认 255 | iOS 常见底色 `#F7F7F9` = 247，按 255 量每个元素墨量系统性偏重 8~12%，看起来像字重错 | 先量全图最常见的灰度当 `--bg`；`elems` 会逐元素核对底色 |
| 1 设备像素的线按整窗墨量判 | 原图的 ±1 灰度雾在几千个像素上积起来比线本身还多：峰值像素级一致的线报 0.863，判成「偏细 14%」 | 清单标 `line`（按峰值行判），或把窗口收到恰好一设备行 |
| 0.1px 一级地微调位置 | Chrome 把布局量化到整设备像素：363.83 和 363.67 渲染逐字节相同，25 次微调全白做 | 每版 `md5sum`，相同就换属性或一次挪 ≥0.3333px |
| 宽度差就全串补字距 | 差集中在开头两个字时，均匀负字距把后面 5 个已对齐的字一起滑开：IoU 0.563 → 0.462 | 先 `cols` 逐字对，看差落在哪几个字上（坑 37） |
| 墨量和 IoU 冲突时听 IoU | 白字按钮：墨量对的 IoU 0.829，墨量偏细的 0.853 —— IoU 依赖只有 ±5% 精度的 Y文字 | 位置 → 墨量 → 相位；IoU 只在墨量相同的候选之间挑 |
| 颜色靠扫字重 | 几何定住后颜色可由墨量一步解出：`Lc = bg − (bg−Lc实测)×(目标/实测)`，一次修好 8 个样式 | 先解颜色；「宽度对、墨量差」先试 text-stroke（不改步进） |
| 中文标题宽度、墨量都对了就收工 | 整串相位仍可能错：13.17px/ls.03 → 13px/ls.27，局部 MAE 12.90 → 6.09 | 字号和字距联合调，判据是逐字列区间 / 局部 MAE |
| 彩色底上窗口框得很大 | 混进更亮的白卡片角，自动 Y 取到 255：真值 0.83 的对勾报成 0.9226 | 窗口内缩到色块里；清单第 9 列钉死 Y文字 |

字重还有一档系统性偏差：iOS 的灰度抗锯齿比 Chrome 的 `antialiased` 粗 8~12%，
这个用 MAE 完全看不出来，只能靠逐行墨量。

## 图标形状

SF Symbols 是光栅资源，没有矢量可导出：

```swift
NSImage(systemSymbolName: "wifi", accessibilityDescription: nil)?
  .withSymbolConfiguration(.init(pointSize: 100, weight: .regular))
// 画进 CGBitmapContext，100 px/pt，输出 PNG
```

再 `python3 scripts/trace_shape.py --image wifi.png --alpha` 追踪成 path。
带孔的图形（圆环、8、o）必须加 `fill-rule="evenodd"`。
`--alpha` 的输出坐标单位是**源图像素**，`viewBox` 直接用源图尺寸，靠 svg 的 CSS 宽高缩放。

截图里的小图标要分两类：

- **字形/复杂轮廓**（问号、徽标、货币符号）：`--image shot.jpg --x X0 X1 --y Y0 Y1 --text-luma N`
  取覆盖度 0.5 等值线，得到的就是那个形状本身，不用去猜字体。
- **几何图元**（箭头、信号条、边框、圆点、胶囊）：**不要追踪**。这类东西的参数空间只有几个数
  （粗细、顶点、圆角、半径），0.5 等值线反而会把 JPEG 光晕一起还原出来 ——
  1 设备像素的边框会追成两三条灰线。直接按参数写 CSS/SVG，用 `iou` 扫参数：
  先定粗细和端点，再定顶点位置。实测箭头 `stroke-width 1.72` + 顶点 1.4 → 0.9605，
  四条信号条 0.9784，圆点 0.9855，胶囊按钮 0.9294 —— 不是「碰巧像」，是扫出来的。

深色主题两个脚本都要加 `--bg`（背景灰度），否则「有没有墨」的判定会把背景算成字；
`--thr` 也要跟着底色走（默认 200 在深底上等于「只认灰度 >200」，见上表）。
深色区块还会让 `rows` 把整块背景当成一行墨、和紧贴其下的文字连成一条带；
深色区里用 `elems` 按元素框，别指望行带切分。

# 指标与坑

下文命令里的 `python3` 在 Windows 上是 `python`；脚本本身不含平台相关代码。

## 三个量测指标

| 指标 | 算法 | 用来判 | 为什么可信 |
|---|---|---|---|
| 墨量 | `Σ clip((255−gray)/255, 0, 1)` 在 bbox 内 | 字重、字号 | 高斯模糊下近似**守恒**。JPEG 把笔画糊开只会让峰值变浅、边缘变灰，总和不变 |
| 覆盖度 | `clip((255−gray)/(255−Y文字), 0, 1)` | 形状、位置 | 对称模糊下，**0.5 等值线 = 真实轮廓位置**，所以能量到亚像素 |
| 列区间 | 逐列「离底色比阈值远」的连通段 | 字号、字距、元素左右沿 | 直接对应 CSS 里的 px 刻度 |

判定阈值（都是实测出来的）：

- 逐行墨量比 **0.97–1.03 算过**，0.93–1.07 勉强，超出就是字号/字重/字距有结构性问题
- 细线（清单里标 `line`）按**峰值行/列**墨量比判，线宽/振铃不参与（见坑 31）；
  判定带 0.90–1.10 —— 源图自己的噪声底就到 7%；整窗比只当参考
- 形状 IoU **> 0.80 好**；0.65–0.80 形状对但边缘差；< 0.5 基本是另一个形状。
  这条只对**强对比、实心**的图标成立（见坑 22、23）；文字和浅灰细线没有绝对线
- 竖向 Δy（墨迹质心）**≤0.75px**。同一段内容在四张卡里重复三次，读数差 0.3px ——
  这是 JPEG 8×8 块相位的噪声底，不是没对齐；门槛设 0.5 会把自己的噪声当误差
- 局部 MAE：**只比同一窗口的改动前后**，没有绝对线（低对比文字 6 上下已经不错，
  深色正文 1–3）。窗口大小不同不可比（见坑 33）
- 全图平均绝对差 **< 7/255** 属于「肉眼看不出差异」的量级

`Y文字` 的取法：把区域内**离底色最远**的前 5% 像素取中位数（浅底上就是最暗的 5%）。
不要直接取最小值 —— JPEG 在锐利边缘会产生 16~24 灰度的过冲，最小值是偏的。

**工具已经替你取**：`box` 会打出 `文字亮度`，`iou` 不给 `--text-luma` 时自动用同一个式子
从原图取（输出里标 `（自动）`）。手填这个数错过一次：拿正文的 118 去量灰度 45 的数字，
IoU 被压到 0.1 级别，而输出格式完全正常，看不出是自己填错了。只有想钉住一个已知值时再传。

`mae` 子命令给全图平均绝对差。它被大片背景稀释，**不能单独判像不像**（见开头那条），
但当整块错位时它比逐行表更早跳：列表整体下移 2px，`rows` 可能每行都「差不多」而 MAE 立刻翻倍。

## 坑

### 1. 量测窗口切在元素边缘

bbox 如果正好贴住窗口边界，量出来的宽高是被裁掉的假值。
踩过一次：period 的量测窗口右边界就是 284.00，于是永远读到「宽 55.00」。
后来又踩了两次（徽标右侧、导航箭头右侧被切），每次输出格式都完全正常，
看上去就是一个「元素窄了 2px」的真结论。

**现在 `box` / `cols` / `elems` 会自己报**，判据是**窗外还接不接着墨**，
不是「墨迹贴着窗口边」：自动生成的清单窗口就是墨迹的 bbox，四边必然贴，
按贴边判会给一份完全正确的清单刷满 `窗口贴边`，人很快就不看这个警告了。
所以工具跳过紧邻的 2 个设备像素（那可能只是 JPEG 振铃），看窗口中段外面
还有没有 ≥25% 的墨。窗口顶到图像边界时外面没有像素，不算剪裁。

看到 `← 墨迹贴右边，窗口可能没框全` 就先放大窗口重测，别拿它当结论。

一条推论：`--thr` 卡得很紧时（比如深底 30 上量灰度 47 的 1 设备像素细线，
阈值只能落 41 附近），**页面底色 19 也会被算成墨**，于是线外侧正常的分界
被判成「贴边」。这不是工具错，是阈值太窄；把窗口收到线本身那一两行，
或者手工确认那条边界就是元素边缘。

### 2. `-apple-system` 在 macOS Chrome 上不是 SF Pro

实测：`-apple-system` / `"SF Pro Text"` / `"SF Pro Display"` / `".SF NS"`
在这些环境下**全部解析成 PingFang SC**（汉字字体），连数字和 `-` 也用它的西文部分。

```js
// 用 canvas 直接验，别猜
c.font = '400 17px system-ui'
c.measureText('2026-09').width
```

实测广播：`-apple-system` 71.48（连字符宽 10.28）vs `system-ui` 68.58（连字符 7.59）。
原图是后者 —— 视觉上 `2026-09` 会变成 `2026–09` 那种长横。

**用 `system-ui`**：西文走 SF Pro，汉字自动回落 PingFang，和 iOS 一致。

### 3. `font-variant-numeric: tabular-nums` 会把数字撑宽

SF Pro 的等宽数字比比例数字宽约 6%。开了之后 `91875.00元` 从 82px 变 87px。
iOS 的列表页一般**不开**，别自作聪明加上去。

### 4. 字号不是整数

实际字号经常是 15.33 / 15.67 这种 1/3 px 的值（3x 截图的设备像素粒度）。
判法：量一个词的墨迹宽度，和 Chrome 在该字号下的宽度比。
有一个「返回」实测 28.33，Chrome 17px 是 31.33 → 真实字号 15.33px。

### 5. iOS 的字干加粗（stem darkening）

iOS 灰度抗锯齿会让笔画比 Chrome 的 `-webkit-font-smoothing:antialiased` 粗 8~12%。
补偿：`-webkit-text-stroke: .1px currentColor`（是可继承属性）。
但**每个样式要单独标定**：数字笔画细，同样的外扩相对增幅更大，实测要 0.16px；
小字号（12px 的 `?`）加了描边会明显过粗，要设回 0。

这个 8~12% 只是起点，不是常数：`text-stroke` 的宽度是绝对值，同样 `.08px`
落在 12px 的字上占比是 28px 的两倍多。标定方法：同一段文字渲两版
（stroke 0 / .08），量出墨量比的差，线性插值到目标 —— 比按「iOS 粗 10%」直接乘准。

### 6. 蓝色在 JPEG 里不可信

4:2:0 色度下采样把细笔画上的饱和度洗掉了。原图量出来灰扑扑的蓝，
不代表真实颜色就是那样。**亮度通道（每像素都有）可信，色度不可信。**
判断方法：对比亮度。原图亮度 127 vs 复刻 118，差值正好是 JPEG 在锐边上的
典型过冲量，所以颜色判定为正确、不改。

### 7. SF Symbols 是光栅资源

没有可提取的矢量轮廓。做法是用 Swift 渲染成 PNG：

```swift
NSImage(systemSymbolName: name, accessibilityDescription: nil)?
  .withSymbolConfiguration(.init(pointSize: 100, weight: .regular))
// 画进 CGBitmapContext，100 px/pt
```

再用 `scripts/trace_shape.py --alpha` 追踪。
`.fill` 变体是描边款，状态栏那种实心图标要用 `.fill` 之外的原始名字。

### 8. 追踪出来的环必须用 evenodd

marching squares 出来的所有环绕向一致，带孔图形（圆环、o、8）
在默认 `fill-rule="nonzero"` 下会被填成实心。加 `fill-rule="evenodd"`。

### 9. 追踪的 Y 轴

直接用图像坐标（Y 向下）输出 path，就别再翻转；
如果沿用「数学坐标 Y 向上」的旧代码，必须配 `transform="translate(0 H) scale(1 -1)"`，
否则图形上下颠倒。

### 10. 追踪前要平滑

截图里的 JPEG 振铃会让 0.5 等值线长出一堆锯齿。
先做 sigma≈0.55 设备像素的高斯，再 8 倍上采样、阈值 0.5。
DP 容差 1.6 网格像素（dpr 3 时 ≈0.067 CSS px）能压到几十个点，肉眼看不出简化。
源图本身就很大时 `--up` 会自动降（见坑 14），此时 1.6 网格像素 = 1.6 源像素，
在 100 px/pt 的图标上只有 0.016pt，仍然可以忽略。

### 11. 中文步进比 1em 宽

本机 PingFang 的汉字步进是 15px @ 15px 字号（1.0em），而某些截图里是 1.027em。
用 `letter-spacing` 补：15.4 − 15 = 0.4px/字。判据是**逐字左沿间距**，不是整行宽度。


### 12. 阈值是「离底色多远算墨」，不是「比某个灰度更暗」

`is_ink` 的真身是 `|bg−gray| > |bg−thr|`：阈值给的是一个**距离**，离底色比它更远的
像素才算墨。浅底上它退化成「灰度 < 阈值」，所以「200」看着像绝对刻度 —— 深底上不是。

浅底 255 + 阈值 200：忽略 200~255 之间的极浅雾，正常。
深底 30 + 默认 200：忽略 `0~200` 的**整段**，等价于「只认灰度 >200 的墨」。
中灰文字（`#6B7078` = 108）、灰色细线——真机上明明是主体内容——全部被当成背景。
实测深色页面 `rows --bg 30` 只切出 **6** 条带，`--thr 80` 切出 **18** 条，
两次输出格式一模一样，区别只是少了 12 行，而汇总行照样报「最大字重偏差 0.0%」。

取 `(最淡元素灰度 + bg) / 2`，也就是把**最淡的那层内容**放在距离中点：

| 底色 | 最淡元素 | 阈值 |
|---|---|---|
| 255 | `#C6C6C6`(198) | 226 |
| 255 | `#999`(153) | 204 |
| 247 | `#C6C6C6`(198) | 222 |
| 30 | `#6B7078`(108) | 69 |
| 30 | 只有白字(255) | 142（此时灰字确实不参与） |

浅灰元素贴着阈值时，亚像素抗锯齿一变 bbox 就跳 ±2px：chevron 是 `#C6C6C6`（灰度 198），
一度因此误判「列表右箭头竖向偏了 1.7px」，换 230 再量其实只差 0.33px。

现在 `rows`/`cols`/`box` 在阈值忽略掉 45% 以上亮度范围时会直接警告
（`!! --thr 200 在底色 30 上把灰度 0~200 当成了背景`），`elems`/`box` 的
「没有墨」也从「坐标不对」改成把被忽略的区间一起报出来。
彩色块内部的 `--bg`（白字蓝按钮的 118、深字橙按钮的 156）不参与这个判断：
那里的底色本来就是中间调，两侧一半在块外，「丢了 45%」没有信息量。

### 13. 底色要量，不能默认 255

上面所有公式（墨量、覆盖度、`gray < 阈值`）都隐含「背景是白的」。
**「浅色」不等于纯白**：iOS 常见的页面底色是 `#F7F7F9`（灰度 **247**），
图标浅色调 `#F3F3F5`（243.5）、`#EFF0F2`（240）。按 255 量，
墨量 = `Σ(255−gray)` 里每一项都多了 8 —— 一个元素系统性偏重 8~12%，
读起来完全像「字重没调对」，盲测为此整轮跑偏。

所以**量之前先看底色**：全图最常见的灰度就是它（`measure.py` 在 `rows`/`mae`
里会自己算，和默认 255 差 ≥3 就警告；`elems` 逐元素核对，判定列写
`底色可能不对（窗口最常见 247）`）。

深底浅字时 `gray < 200` 会把整个背景当成墨，行带切分直接崩掉；
反过来给对了 `--bg` 却留着默认 `--thr 200`，中灰文字又会被整段当成背景（坑 12）。

两个脚本都接受 `--bg`（背景灰度，浅底默认 255）：

```bash
python3 measure.py --bg 20 rows --orig a.png --mine b.png
python3 trace_shape.py --image d.png --x .. --y .. --bg 20 --text-luma 240
```

公式是故意写成对 `--bg` 对称的，浅底/深底共用一套：

| 量 | 浅底 | 深底 |
|---|---|---|
| 墨量 | `Σ\|bg−gray\|/255` | 同一个式子（取绝对值，方向自动翻转） |
| 覆盖度 | `(bg−gray)/(bg−Y)` | 同一个式子（分子分母同时变号） |
| 有墨判定 | `\|bg−gray\| > \|bg−thr\|` | 同一个式子 |

`--bg` / `--dpr` 写在子命令前后都可以（脚本两个位置都收；早先只能写在前面，
写在后面会报 `unrecognized arguments`，而报错完全不提示该挪位置）。
实测 dpr=2 的合成圆（半径 6px，浅底/深底各一张）：两者追踪面积一致，
与解析值 113.097 相差 0.5~0.7%，全部来自 DP 折线内接于圆，不是 `--bg` 的误差。

### 14. `--alpha` 的输出单位是源图像素

图标 PNG 一般按 100 px/pt 渲染（见坑 7），追踪出来的 `viewBox="0 0 1800 1300"`
就是 18×13 pt。给 `<svg>` 设 `width="18px"` 即可等比缩放，不要再去乘除 100。

`--up` 会按工作网格 2600 自动封顶：1800px 宽的图标自动降到 `--up 1`，
否则纯 Python 的 marching squares 要在 14000×10000 的网格上跑（实测 40 秒）。
正常情况 0.3 秒出结果，环数不受影响（wifi 3 环、cellularbars 8 环）。

### 15. `--window-size` 定不了视口（本工具踩过的最贵的坑）

macOS 的 Chrome 有个最小窗口宽度，`--window-size=390,844` 实际给出的视口是
**500×757**，而截图仍然按请求的 390×844 裁 —— 页面按 500 排版、只截左边 390。
规则验证方式：放一张写着 `innerWidth + "x" + innerHeight` 的探针页，
渲染出来读数字，别信命令行参数。

后果：`.phone{width:390px}` 居中后左边多出 55px，右边缘被切掉，全页 x 坐标作废，
而且**逐行墨量比看起来很接近**（整行求和把横向裁切平均掉了），只有 bbox 和 IoU 会突然掉到 0.1。
有一次就是这样一路量到「IoU 0.82」之后才发现渲染器是坏的。

`scripts/render.py`（`render.sh` 是它的包装）的做法：套一层固定 `宽×高` 的 iframe，窗口开大一点，
页面在 iframe 里拿到真正的 390×844 视口，截完按 `宽×dpr` 裁左上角。

**自查**：任何一次渲染，先确认 `innerWidth` 等于你要的宽度。这一条比后面所有指标都优先。

### 16. 内容盒原点要从「实心元素」反推，不能从文字反推

`--side` 原来写 16，实测应该是 **16.67**（＝50/3 设备像素）。判据不是文字的墨迹左沿 ——
那里面混着字体侧边距，±0.7px 分不清是原点偏了还是字宽不一样 —— 而是**分隔线**：
它是一条纯色细线，两端就是元素边界，量到设备像素 50 和 1120 正好对称。

改这一个数，全图 MAE 从 5.996 掉到 3.998。原因是 0.67px 的原点误差会把**每个字**
都平移 0.67，而逐元素的 bbox 自查看不出来（每个元素和自己比都是「对的」）。
所以：**先量实心边界定原点，再量文字**。实心元素包括分隔线、色块、卡片边、图标的直边。

### 17. 0.5px 的分隔线会摊成两行、峰值偏浅

汇总里的那条横线：原图在 3 个设备行上是 30/3/8 的灰度差，按墨量守恒折成一根 1 设备像素
的实线是 `rgba(0,0,0,.161)`（214）。用 `box-shadow: inset 0 .5px 0` 画，0.5px ＝1.5 设备像素，
必然跨两行、峰值只有 238/246 —— 积分差不多，看上去更浅更毛。

```css
/* 1 设备像素的实线：位置要落在设备像素整数边界上 */
.sep::before{content:"";position:absolute;left:16.67px;right:16.67px;top:0;
  height:.3333px;background:rgba(0,0,0,.161)}
```

**先看它散在几行**：散在 1~2 行 → 1 设备像素实线；散在 3~4 行且是渐变 → 那是带模糊的阴影，
用同样高度的一段渐变复现（导航底边实测 4 行 18/25/28/26 → 1.333px 渐变，局部 MAE 4.49 → 0.95）。
两种都按**积分**取 alpha，别按峰值取。

### 18. 改一块的内边距，必须同时在另一侧补回来

汇总块 `padding:14px 0` 改上边 12.67px 之后，下面**整屏列表**跟着上移 1.66px，
MAE 从 3.7 反弹到 5.4。行表里只表现为第一行 `Δy −1.3`，很像「某一行没对齐」。

改成 `padding:12.67px 0 14.33px`，总高保持 90 不变。**动一个块的上内边距时，
先记下这个块的总高，改完把差额补到下内边距上**；块高变了，下面全部元素都会跟着动。

### 19. 容器一动，里面每个「校准过」的子元素都要重标

徽标上原来写着 `top:-.67px`，注释是「比 flex 居中高 0.67」——那是错的：
它当时是**在补偿行本身偏低 1.33px**。行修好之后，同一个徽标反而高了 0.67，得改成 `+.665px`，
`margin-left` 也从 6.66 改到 5.99（原点挪了 0.67）。

判据：修好容器后，子元素的偏差会**正好按你刚才移动的量翻号**。所以先修容器、再逐个重量子元素。
反过来说，当年那个「徽标已对准」的结论是假象 —— 同一行里的文字偏了 1.33，徽标却是准的，
**逐个子元素量**才看得出来，整行一个 bbox 会把它平均掉。

### 20. 字号一变大，flex 基线对齐会让行盒长高

`.item-period` 从 17px 改到 17.67px（宽度才对齐）之后，`align-items:baseline` 的那一行
高出 0.25px，四张卡片累积下来页面底部错位 1.5px。

`line-height:24px` **挡不住**：flex 行的交叉尺寸是
`max(基线以上) + max(基线以下)`，不是 line-height。要在容器上钉死 `height:24px`
（内容溢出 0.25px 无所谓，那是字框不是可见墨迹），然后再用相对定位把子元素挪回原位。

还有一层：`line-height` 只定行盒高度，**基线在行盒里的位置由字体的 ascent/descent 决定**。
所以同一个 `line-height:1` 下，中文行和西文行的基线不在同一高度（PingFang 和 SF Pro
的度量不同）—— 「行高一样」不等于「基线一样」。跨字体对齐一律用固定 `height` +
相对定位，别把 line-height 当垂直居中的旋钮。

### 21. 宽度差先补字距；改动之前先把「锚点」修对

汇总数值比原图宽 2.9%，试了字号 15.22/15.33 和字距 −0.19…−0.35，**每一种都把 IoU 改差**
（0.56 → 0.43）。因为墨量本来是对的，缩小字号或压字距换来的是「每个字都从原图的笔画上滑开」，
而宽度差只是在字符串末端累积 2px。

- 墨量对、宽度差 → 只加 `letter-spacing`（不改笔画粗细）：导航标题宽 1.67 → 字距 .2 → .534，bbox 立刻严丝合缝。
- 墨量不对 → 才动字重/字号。
- **判定用 IoU，不用宽度**。宽度对上但每个字错位，是更差的结果。

还有一个顺序问题：右边对齐的字符串，容器的右内边距错了会**伪装成字号错**。
日期在 17.67 时 IoU 只有 0.15（比 17.33 更差），真凶是 `.item-head` 的 `padding-right`
（35 应为 33.33）—— 锚点错 1.67，字号再准也没用。**扫字号之前，先把锚点量准闭嘴。**


### 22. 文字也要算 IoU —— 它是唯一看得见「亚像素相位」的指标

bbox 四边全 0、墨量 0.997、行比值 1.000，三个指标全过，一段「实付金额」的 IoU 只有
**0.7054**：每个字形都比原图偏 0.33px。给这行补 0.14px 字距后 IoU 0.925，
同一步把全局 MAE 从 0.444 压到 0.380 —— 比任何一次字号/位置调整都大。

但**文字的 IoU 没有绝对门槛**，它的底噪取决于渲染器是否同源：

| 原图来源 | 文字 IoU 的现实水平（bbox 与墨量已达标时） |
|---|---|
| iOS 截图，深色正文 | 0.72–0.85（实测日期 0.72，bbox 全 0、墨量 0.995） |
| iOS 截图，浅灰 `#999` 正文 | **0.52–0.67**（实际颜色越浅，JPEG 噪声在覆盖率里占比越大） |
| Chrome 渲染的图（同源栅格化） | 0.93–0.99 |

所以只看**同一页、改动前后**的 ΔIoU：升了留、降了回滚。不要拿 0.80 去卡 iOS 原图的正文，
那会逼你去拟合 JPEG。强对比的实心图标不受这条影响，照旧 > 0.80。

**例外：细描边 + 低对比的图标同样有底噪。** 1 设备像素宽的 `#C6C6C6` 箭头
（背景 255、文字亮度 206，只差 49 个灰度）实测 bbox 四边都在 1 设备像素内、墨量差 2.5%，
IoU 却只有 **0.539** —— 对比度低，JPEG 噪声在覆盖率里占的比例被放大。
`elems` 因此只对 `icon` 且 `|bg−Y文字| ≥ 100` 的元素按 0.80 判形状；
浅灰细线图标和文字一样，只比改动前后。

### 23. 白字在彩色底上：`--bg` 和 `--text-luma` 必须同时给

覆盖率公式假设「背景亮、字暗」。白字压在 `#3A7DF0`（灰度 118）的按钮上时，
如果只给 `--text-luma 255`、背景还用默认 255，算出来的是**整块底色**的形状：

- 默认参数：IoU **0.9373**（看着很好，其实是按钮本身）
- 给 `--bg 118 --text-luma 255`：IoU **0.8072**（真正的字形）

两次输出格式一模一样，没有任何提示。现在 `iou` 在「窗口内一半以上被算成墨」时
会打警告 —— 看到就别信那个数，先把底色交上去。
文本行同理：深色卡上的浅字要给 `--bg`（卡底色），不是 255。

### 24. IoU 先对齐，再判形状

`iou` 只比同一坐标。1 个设备像素的位置差可以把箭头从 **0.9605 压到 0.7994**，
正好压过 0.80 的线，看起来像「形状不对」，于是人会去改路径 —— 越改越差。

```bash
python3 measure.py iou ... --x .. --y .. --shift 4
# 最佳对齐 IoU 0.9605（复刻需移 dy=-1 dx=+0 设备像素），原地 0.7994
```

顺序是 **(dy, dx)**，**y 在前**。早先只印 `-1,+0`，盲测里把该往上移的箭头横着移了
一格 —— 现在两个分量都带名字。

两句一起看：**最佳对齐高、原地低 = 位置错**（改 CSS 定位）；
**两者都低 = 形状错**（改路径/参数）。对齐后再扫形状参数。

### 25. 几何图元用参数扫描，不要用追踪

`trace_shape.py` 的 0.5 等值线对**有机轮廓**（wifi、问号、字母形）是对的，
因为那里模糊是对称的、轮廓本身有宽度。但对 1 设备像素的描边（标签边框、细箭头、
下划线），等值线会把 JPEG 光晕一起还原成两三条灰线，比直接画还差。

几何图元的做法：写参数 → 渲染 → `iou`，扫参数。实测一条箭头（`stroke-width` × 顶点位置
× 端点样式）从 0.7994 扫到 0.9605；四条信号条 0.9784；4.3px 圆点 0.9855；
126×41 胶囊 0.9294。二维网格扫描通常 20–40 个变体就够，比调路径直观。

### 26. 下划线的位置是 1/3 px 级的

`text-decoration:underline` 的默认位置和原图经常差一个设备行。
实测 `text-underline-offset:1.4px` 时线落在原图下一行、前导行只有 luma 228（原图 141），
IoU 0.8038；改成 `1.1px` 后四行都是 141，IoU 0.8848；另一个链接 0.8925 → 0.9829。

做法：先 `cols` 量出线所在的设备行（它是横贯整段的连续段），再扫 offset 到线正好压上去。
扫不到就放弃原生下划线，画一条独立的 `height:1.3333px` 色条 —— 位置和粗细都可控。

### 27. 字重不是三档，但也不是处处连续：西文按 50 变，中文按脸量化

原图的字重经常落在中间。实测金额 `28px / 700` 比原图重 11.6%，改成 `29px / 550`
才同时对上宽度和墨量（0.995–0.996、bbox 全 0）；货币符号要 450。
`-webkit-text-stroke` 也同样：`.1px` 在 11–12px 上明显过粗（要 .04–.05），
15px 的细数字要 .08。

**但「连续」只对西文成立**（上面那个金额是数字，走 SF Pro）。汉字回落 PingFang，
`font-weight` 会被量化到整张脸 —— 28px 纯中文、dpr 3，逐字节 md5 实测：

| font-weight | 100 | 200–300 | 350–450 | 500 | 550 | 600–800 |
|---|---|---|---|---|---|---|
| 落到哪张脸 | Ultralight | Thin | Regular | Medium | **合成加粗** | Semibold |
| 墨量（Regular = 1） | 0.41 | 0.56 | 1.00 | 1.26 | **1.52** | 1.36 |

两件事：400 和 450 渲染**逐字节相同**（在这上面扫字重是空转，配合 `md5sum` 那条看）；
**550 比 600 还重 12%**，墨迹还外扩 0.67px —— 它不是中间档，是 Chrome 的合成加粗。
中文调字重按 300/400/500/600 四档走，落在两档之间的用字号和描边补；
纯西文（`system-ui` → SF Pro）才是每 50 一档都真的变。

所以标准动作是 **size × weight × stroke 三维小扫描**，判据三件套：
宽度、墨量比、IoU。只扫字号或只加描边，都会卡在「宽度对了但粗细不对」。

### 28. `字干` 列在含图形的行上不可信

行带里有徽标边框、按钮圆角、信号条时，水平游程的中位数量的是**图形的边**，不是字干。
实测两行报「字干原 0.67 / 复 1.00」和「2.00 / 2.67」，墨量比却是 0.993 / 0.996 ——
字干差 30% 但完全没问题。

`rows` 现在会在「字干差 >25% 且墨量正常」时标注
`（字干差但墨量正常：行内含图形，别追）`。看到这句就跳过这一列，以墨量和 IoU 为准。

### 29. 自动 `Y文字` 在「墨很少」的窗口里会退化成背景

`text_luma` 取「离背景最远 5% 像素的中位数」。**窗口里墨不到 5% 时，95% 分位数落在背景上（=0），
整窗都被选中，中位数就是背景本身**。Y=bg → 覆盖率分母为 0 → 覆盖率整块归零。

实测：22×50 CSS px 的窗口里一条 7×12 的浅灰箭头，墨只占 **2.2%**，
**同一张图跟自己比 IoU 0.000**，而四边 Δ 全 0、墨量比 1.000 —— 输出格式完全正常，
唯一的线索是「0.000」低得不可能是真的。同一页相邻的箭头（窗口更紧）却是 1.000，
所以连「和同页其他元素比」都看不出来。

现在 `text_luma` 用 `max(95% 分位数, 0.5 × 峰值对比度)` 兜底，保证选中的一定是墨的核心；
`iou` / `elems` 再遇到「自动 Y ≈ 背景」（差 < 4 灰度）会直接报「窗口里没有可测的墨」，
不再打印一个 0.000 让你去改本来正确的路径。

**通用教训：清单先在原图上自比一次。**

```bash
python3 measure.py elems --orig 原图 --mine 原图 --rects rects.txt
```

四边必须全 0、墨量比必须 **1.000**、IoU 必须 **1.000**。任何一项不是，
先怀疑窗口/阈值/工具，别去改 CSS。这一步是零成本的，比事后分辨「这个 0.54 到底是
底噪还是真错」便宜得多。

### 30. 深色/彩色底上的行带会吃掉整块背景

`rows` 默认 `bg=255`。深色 hero 区块会被当成「一整行墨」（0–142.7），
和紧贴其下的第一行文字连成一条带，看不出里面有几行。深色区块内要单独量：
给 `--bg`（底色灰度），或者直接用 `elems` 按元素框，别指望 `rows` 的自动切带。

### 31. 细线按整窗墨量判：振铃积起来比线本身还多

一 条 1 设备像素的线被 JPEG 糊开后，在窗口范围内留下 ±1~3 灰度的雾。
窗口有几千个设备像素，这点雾积起来**比线本身还多**，整窗墨量比于是一个正确的线
被判成「偏细 14%」：

| 元素 | 峰值灰度（原/复） | 整窗墨量比 | 峰值行/列墨量比 |
|---|---|---|---|
| 下划线（300px 宽窗口） | 235.61 / 236.56 | **0.863** | 1.000 |
| 卡片分隔线（342px 宽窗口） | — | **0.904** | **1.000** |
| 底栏顶线 | — | 1.027 | 1.000 |

**做法**：清单里把这类元素标成 `line`，工具就按峰值行/列判（并列印
`细线（整窗比 0.904 含背景振铃，看峰值）`）；手工量时把窗口收到**恰好一设备行**
（y0=460.667 / y1=461），或者 `box` 看峰值灰度。

**竖线按列看。** 工具取的是「短轴」那一维：横线看峰值行，竖线看峰值列。
拿行去量一条竖线，一行里只有一两个像素的墨，读数是噪声（实测同一根竖线
按行 0.800、按列 1.070，差的方向和大小都像是「形状错了」）。

**判定带是 0.90–1.10，不是 0.97–1.03。** 源图自己的噪声就有这么高：同一页两条
一模一样的线，峰值墨量 42.1 vs 42.9（差 1.9%）；单条线赶上 JPEG 8×8 块的相位能到 7%。
真实的粗细错（alpha .08 vs .12）是 30% 以上，不会藏在这条带里。

### 32. Chrome 把布局量化到整设备像素，0.1px 的微调常常什么都没改

`sect{top:363.83}` 和 `363.67` 渲染出来**逐字节相同**（局部 MAE 都是 12.90）。
3x 下文字的基线和边框都落到整设备行，亚像素的 y 只改抗锯齿相位、不改位置；
第二次盲测在这类「无效微调」上烧了约 25 次渲染。

**做法**：每改一版先 `md5sum` 渲染图。和上一版字节相同 = 这个旋钮死了，
换一个属相或者一次挪 ≥1 设备像素（0.3333 CSS）。同理，改完之后**不要**用
「还差 0.07px」说服自己继续调 —— 那是量测噪声。

### 33. 局部 MAE 是低对比文字上唯一稳的绝对信号

全图 MAE 被背景稀释，不能判像不像 —— 但**同一个窗口内的 MAE** 不是：
盲测里 sect 的局部 MAE 12.90 → 10.21 → 9.70 → 6.09 一路指明方向，
而它的宽度和墨量在起点就已经「合格」（IoU 0.818，墨量 0.988）。

`elems` 现在每行都报 `MAE局部`。用法和文字 IoU 一样：**只比自己改动前后**，
窗口大小不同的元素之间不可比（一个 350px 宽的窗口混进大片背景，MAE 天然小）。

### 34. 颜色是可以解出来的，不用扫

几何定住之后，颜色由墨量一步解出来：

```
Lc = bg − (bg − Lc_实测) × (墨量目标 / 墨量实测)
```

实测一次修好 8 个样式（sect 墨量 0.956 → 1.002，几何完全不变）。
前提：字形是纯色填充（没有渐变、阴影、发光），且 `--bg` 给对了。
这比「扫字重」快一个量级：改颜色只改反差，不改形状和步进。

它有个边界：**颜色只能在底色和 0/255 之间取**。最暗的墨已经贴到 0 时，
再往深解会得到负数（`Lc = 255 − 235 × 1.14 ≈ −13`）—— 那个缺口不在颜色上，
在描边或字重上，改颜色永远补不满。所以先看解出来的 `Lc` 是否落在 0~255 之外：
撞墙就以局部 MAE / IoU 为准回去查几何和描边，别在颜色上反复扫。

`-webkit-text-stroke` 是另一条路：它加粗**墨迹**但不改**步进**，
所以「宽度对、墨量差」时先试描边，别动字号。

### 35. 墨量和 IoU 打架时，听墨量的

同一次盲测里，白字按钮：

- 墨量正确的配置：墨量 0.999，IoU **0.829**
- 墨量偏细的配置：墨量 0.970，IoU **0.853**

IoU 依赖覆盖率的分母 `Y文字`，而 Y 只有 ±5% 的精度；墨量对模糊守恒，是可积的。
优先级：**位置（Δ）→ 墨量（字重/颜色）→ 相位（IoU / 局部 MAE）**。
IoU 只在**墨量相同的候选**之间做选择。

### 36. 中文标题：字号和字距要联合调

宽度 51.67（两边一致）、墨量 0.988，整串相位仍然错。
`13.17px / letter-spacing .03` → `13px / .27`：局部 MAE 12.90 → 6.09，
IoU 0.818 → 0.916，而**宽度和墨量前后几乎没变**。

汉字步进和 Chrome 的设备像素量化互相咬合：字号定整串宽度，字距定每个字落在哪。
所以「宽度对 + 墨量对」不等于「相位对」；判据是逐字列区间（`cols`）和局部 MAE。
这是「宽度差才补字距」这条规则的反例 —— 宽度没差，字距照样是有效变量。

### 37. 宽度差：先看它落在哪几个字上，再决定用不用字距

右对齐的 `91875.00元` 比原图宽 2.33 CSS px。逐字段一看，**从第 3 个字起，
两边每个字的列区间都在 0.33px 内**，多出来的 2.33px 全在开头的「91」上
（也许是 SF Pro 的字距表/kerning 差异，不是字号）。

均匀负字距能把左沿从 −6 拉回 0，但会把后面 5 个本来对齐的字一起滑开：

| letter-spacing | Δ左 | IoU | 局部 MAE | 全局 MAE |
|---|---|---|---|---|
| 0（现状） | −6 | **0.563** | 7.98 | **3.147** |
| −0.10 | −4 | 0.600 | 7.31 | 3.146 |
| −0.20 | −1 | 0.535 | 8.49 | 3.315 |
| −0.25 | 0 | **0.462** | 10.14 | — |

所以「墨量对、宽度差 → 补字距」有个前提：**差是均匀分布的**。
先用 `cols` 逐字对一遍；差集中在个别字上时，字距是错的工具。
代价是 2 CSS px，全局 MAE 说明它已经是最优 —— 接受它，别为了 Δ=0 去拟合。

`elems` 把这一步做成了结论版：段数两边一致时，按**首尾字心跨度**算整串长度比，
差 ≥3% 才开口；再看亚像素字宽比 —— 跟着一起变是字号/缩放，没变是字距：

| 跨度比 | 字宽比 | 归因 |
|---|---|---|
| 1.04 | 1.00 | 字距 |
| 1.04 | 1.04 | 字号 / 缩放 |

差集中在开头几个字时，那不是均匀差，回到 `cols` 逐字看。

字宽量的是列剖面的 **0.5 峰值交叉点**（对称模糊下它正落在真实边缘），不是「有墨的列数」：
后者被 JPEG 光晕和整像素舍入撑宽 —— 实测同一段文字按掩膜差 6.2%、按交叉点差 0.1%，
足够把一个正确的字号判成整档错。段数不同时工具不开口：相邻字并段很常见
（实测一页好图上有 3 个元素两边段数不同），拿它当结论就是拟合噪声。

### 38. 测彩色底上的元素：窗口要整个落在色块里

`iou` 的自动 Y 取「离背景最远的那撮像素」，但窗口里如果混进**比底色更亮**的东西
（白色卡片的圆角、反光），旧公式会把它当成墨：一个真值 0.83 的对勾报成
**0.9226**，格式完全正常。现在加了 `0.5×峰值对比度` 兜底，同一个窗口自动 Y=67
（真值 65）、IoU 0.838。

仍然建议两道保险：窗口内缩到色块里（28×28 的圆取中间的 16×16），
以及在清单第 9 列直接钉死 Y文字：

```
按钮,30,360,500,540,,118,icon,255
```

`elems` 还会逐元素核对底色：窗口里最常见的灰度（占比 ≥25%、且不是墨自己）
和给的 `--bg` 差 ≥3 灰度时，判定列写 `底色可能不对（窗口最常见 240，按它算墨量比 1.000）`
—— 括号里的数是按**窗口自己的底色**重算的，和「墨量比」列并排一比就知道原来那个数偏了多少。


## 别做的事

- 不要靠肉眼比对截图就宣布完成。差异 1px 在缩略图里看不出来，在 3x 原尺寸下非常明显。
- 不要在没对齐版式的情况下调字重。行数对不上、元素错位时，墨量比没有意义。
- 不要为了「更接近」而去拟合 JPEG 的模糊。模糊是压缩产生的，
  真实 UI 是清晰的 —— 以 0.5 等值线（真实轮廓）为准。
